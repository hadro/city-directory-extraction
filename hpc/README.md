# Running the city-directory fine-tune on NYU HPC (Torch)

Self-contained bundle for training the Qwen3.5 city-directory extractor on a SLURM cluster.
Written for **NYU Torch** ([docs](https://services.rt.nyu.edu/docs/hpc/)); the "Porting to another
cluster" section at the bottom covers what changes elsewhere.

> **Torch, not Greene.** Greene was decommissioned **2026-01-30** and replaced by Torch. Most
> NYU-HPC material you'll find online — blog posts, GitHub tutorials, older lab wikis — is
> Greene-era and will mislead you on four specifics this bundle gets right:
> **Apptainer** (not Singularity) · images under **`/share/apps`** (not `/scratch/work/public`) ·
> a **mandatory `--account`** · GPU selection via **`--constraint=h200`** (not the typed
> `--gres=gpu:a100:1`, which Torch does not accept).

**The short answer to "can this run on NYU HPC?": yes, comfortably.** This is a 0.8B-parameter
LoRA fine-tune on 100k short text examples — a *small* job by HPC standards. It needs one GPU
for a few hours, no multi-node anything, no MPI, no distributed training. The measured reference
run is **2.6 h on a single rented RTX-Pro-6000, ~$7** — and Torch has that exact card, plus 232
H200s that are faster still. The entire model is 1.6 GB and the training data is 35 MB.

The real work of the port is not compute, it is three environment differences:

| | commercial GPU rental (what we've been doing) | Torch |
|---|---|---|
| environment | ephemeral container, `pip install` at job start | persistent, and a naive pip install blows the **30K inode** quota on `/home` |
| network | job downloads the model itself | assume **no outbound internet on compute nodes** — pre-stage everything |
| interruption | job runs to completion | **wall-clock limits** + preemption — need checkpoint/resume |

All three are handled by the scripts here.

## Before you start: access

Torch needs an NYU NetID plus an HPC account, **and** — this is the part that differs from most
clusters — **an active allocation in the HPC projects portal**. Without one you cannot submit any
job at all: `--account` is mandatory, not optional. That allocation is what the Law School center
would actually be giving you. Settle these up front:

1. **An HPC account *and* a project allocation.** Once you have both, `my_slurm_accounts` on the
   login node prints the account string — put it in `SLURM_ACCOUNT` in `env.sh`. (`env.sh` warns
   you if it's unset.)
2. **Which GPU constraints your allocation can request.** Torch has H200 / L40S / A100 / H100 /
   RTX-Pro-6000, but stakeholder QoS controls what *you* can reach. Ask which, and what the
   wall-clock ceiling is — the docs mention a 24-GPU-per-user quota for jobs under 48 h, which
   suggests 48 h is the practical planning boundary, but confirm.
3. **Whether compute nodes have outbound internet.** NYU doesn't document this either way. These
   scripts assume *no* and pre-stage everything, which is safe regardless — but if they do, you
   can skip a step.
4. **Whether the gold eval data is OK to put on their filesystem.** The NYU 1850 gold is
   CC-BY-SA-NC and the panel gold is hand-labeled from library scans; both are gitignored in this
   repo deliberately. `make_bundle.sh --no-gold` omits them if that conversation needs to happen
   first. (NYU-derived data sitting on NYU infrastructure is not obviously a problem, but ask.)

Nothing here requires paid API access. The synthetic training data is generated by this project
and license-clean; the base model is open-weights.

## Quick start

**On your laptop**, from the repo root:

```bash
bash hpc/make_bundle.sh                      # -> cde-hpc-bundle-<sha>.tar.gz  (~6 MB)
scp cde-hpc-bundle-*.tar.gz <netid>@<torch-login-host>:/scratch/<netid>/
```

(Get the exact login hostname from the Torch docs or your account email — it is not the old
`greene.hpc.nyu.edu`.)

**On Torch:**

```bash
ssh <netid>@<torch-login-host>
cd /scratch/$USER
tar xzf cde-hpc-bundle-*.tar.gz
mv cde-hpc-bundle-* city-directory-extraction
cd city-directory-extraction

# 1. configure — set SLURM_ACCOUNT (REQUIRED on Torch) and GPU_TYPE
my_slurm_accounts                            # prints the account string to use
vim hpc/env.sh
source hpc/env.sh

# 2. build the environment (~15 min, login node)
bash hpc/00_setup_env.sh

# 3. stage the base model + check the data (~5 min, login node)
bash hpc/01_prefetch.sh

# 4. smoke test (~10 min on a GPU) — DO NOT SKIP
sbatch $(slurm_gpu_args) hpc/10_smoke.sbatch
squeue -u $USER                              # watch it
tail -f logs/smoke-*.out

# 5. the real run
sbatch $(slurm_gpu_args) --time=$TRAIN_TIME \
       --export=ALL,RUN_NAME=v6 hpc/20_train.sbatch

# 6. score it
sbatch $(slurm_gpu_args) --export=ALL,RUN_NAME=v6 hpc/30_eval.sbatch
cat results/eval_table.md

# 7. publish (login node — compute nodes can't reach the Hub)
export HF_TOKEN=hf_...
bash hpc/40_push_adapter.sh v6 hadro/city-dir-08b-yaml-v6
```

`slurm_gpu_args` (defined in `env.sh`) expands to
`--gres=gpu:1 --constraint=$GPU_TYPE --account=$SLURM_ACCOUNT` — Torch's GPU-selection form.
It deliberately does **not** set `--partition`: NYU's docs say don't specify partitions manually,
since QoS on your account governs access.

## GPU choice

Set `GPU_TYPE` in `env.sh`; it becomes `--constraint=<type>` and drives batch size, grad-accum and
the default `--time`. Torch's inventory, with estimated wall-clock for the **0.8B / 100k × 3**
reference run:

| GPU | VRAM | count | batch | est. 100k run | note |
|---|---|---|---|---|---|
| **H200** | 141 GB | 232 | 64 | **~1.6 h** | biggest *and* fastest. The headroom matters at 4B — see below. |
| **RTX-Pro-6000** | 96 GB | 16 | 64 | ~2.2 h | **our measured card** (31.4 samp/s) — but only 16 on the whole cluster. |
| **H100** | 80 GB | 60 | 64 | ~1.8 h | |
| **A100** | 80 GB | 172 | 64 | ~3.3 h | the measured baseline (21.1 samp/s). Some nodes may be 40 GB — verify. |
| **L40S** | 48 GB | 272 | 32 | ~6 h | most numerous, so likely shortest queue; slowest here (bandwidth-bound). |

Only the A100 and RTX-Pro-6000 figures are anchored in measurement; the Hopper and L40S numbers
are deliberately conservative estimates, because this workload runs on a slow torch-fallback
kernel path and is launch-bound rather than FLOP-bound — newer cards deliver much less than their
spec-sheet multiple here. **Run the smoke job and feed the real throughput back in:**
`python3 hpc/estimate_run.py --measured <samp/s>`.

Every Torch GPU is Ampere-or-newer, so precision is always bf16 (`sft_qwen.py` auto-selects); the
fp16 fallback only mattered on Greene's Turing/Volta cards.

**Do not reach for multi-GPU.** At 0.8B with this batch size the run is not VRAM-bound and the
bottleneck is a slow kernel fallback, not parallelism — measured attempts at bigger batches and
at Unsloth both came out *slower*. One GPU, longer wall clock, is the right shape.

## Scaling to 2B and 4B — the actual reason to want a cluster

The 0.8B run costs ~$7 rented; nobody needs free compute for that. **The family scale-up is
where an HPC allocation changes the picture.** Set `MODEL_SIZE` in `env.sh` (`0.8B` | `2B` | `4B`)
and everything else — batch size, grad-accum, wall-clock request — follows automatically.

Run the estimator for your exact config; it's stdlib-only and runs on your laptop:

```bash
python3 hpc/estimate_run.py                          # full table
python3 hpc/estimate_run.py --n 500000 --size 4B     # one config
python3 hpc/estimate_run.py --measured 12.4          # re-anchor on YOUR smoke throughput
```

**500k examples × 3 epochs** (the Mattingly-scale target), estimated:

| model | H200 (free, Torch) | A100 (free, Torch) | L40S (free, Torch) | rented rtx-pro-6000 |
|---|---|---|---|---|
| 0.8B | ~8 h, 1 job | ~17 h, 1 job | ~30 h, 1 job | ~11 h, **$30** |
| 2B | ~23 h, 1 job | ~54 h, 2 jobs | ~98 h, 3 jobs | ~36 h, **$99** |
| 4B | **~42 h, 1 job** | ~99 h, 3 jobs | ~181 h, 4 jobs | ~67 h, **$183** |
| **family total** | **~73 GPU-h** | ~170 GPU-h | ~309 GPU-h | **~$310** |

"jobs" = chained SLURM submissions at a 48 h wall-clock cap. The estimator is calibrated against
the two runs we actually measured (it reproduces the proven 0.8B/100k A100 run at 3.9 h and the
rtx-pro-6000 run at ~$6), but everything at 2B/4B is extrapolation — **run the smoke job and feed
the real number back in with `--measured`.**

**The H200 row is the headline.** On Greene-era hardware the 4B/500k run was a 3-to-7-link chained
job spanning a week or more of calendar time. On Torch's H200s it's a **single ~42 h job** that
fits inside one 48 h allocation — no chaining, no multi-day babysitting. That single fact is most
of the argument for using Torch on the family scale-up.

### The surprising part: VRAM is not the constraint

Qwen3.5 has a **248,320-token vocabulary**, and the loss path materialises a
`[batch × 512 × 248320]` logits tensor which then gets upcast to fp32. At batch 64 that single
tensor is ~57 GB — far larger than any of these models' weights. It's also the explanation for
the OOM this project already hit at batch 16 on a 24 GB L4.

The consequence is counterintuitive and useful: **that term doesn't scale with model size.** Going
0.8B → 4B adds ~7 GB of weights to a ~60 GB budget. A 48 GB L40S can train the 4B at batch 16; an
80 GB A100 at batch 32; a 141 GB H200 at the full batch 64. **Batch size, not parameter count,
sets the VRAM wall** — which is exactly why the H200's extra memory converts directly into speed
here rather than merely into "fits". `env.sh` holds the *effective* batch at 64 everywhere via
grad-accum, so a smaller card changes throughput but not the optimization trajectory — the family
runs stay comparable to the 0.8B board.

### The actual constraint: wall clock × queue

On an H200 every run in the table fits one 48 h job and none of this applies. On A100/L40S the 2B
and 4B runs don't: a 4B/500k on L40S is ~181 GPU-hours against a per-job cap that Torch's docs
imply is 48 h (**confirm yours**: `sinfo -o "%P %l"`, or ask). Those runs have to survive being
killed and resumed. That's what `50_chain_train.sh` is for:

```bash
source hpc/env.sh                       # with MODEL_SIZE=4B, GPU_TYPE=l40s
bash hpc/50_chain_train.sh 4 v6-4b      # 4 dependent jobs, each resuming the last
```

Each link waits on the previous with `--dependency=afterany` — *any*, not *ok*, because a
wall-clock kill exits non-zero and that's precisely the case the next link must handle. Combined
with `--resume-from-checkpoint auto` and 500-step checkpoints, each restart costs minutes. Once
training actually completes, leftover links resume a finished run and exit immediately, so
over-requesting links is harmless.

**Budget calendar time, not GPU time.** Each link re-enters the queue. A 4-link L40S chain is free
but could span a week or more of wall time. That is the real trade — and it's the trade you avoid
by getting an H200.

### Which to run where

- **0.8B iteration (the current cycle) → keep renting.** $7 and same-day turnaround. The project
  is in a fast data-iteration loop; a queue wait costs more than the money saves.
- **2B and 4B at 500k → Torch.** This is $280 of the ~$310 family bill, and they're one-off runs
  where queue latency doesn't hurt.
- **Ask for H200 access specifically.** It's the difference between the 4B/500k being one 48 h
  job and being a 4-link chain across a week. With 232 of them on the cluster it's not an
  unreasonable ask. L40S is the fallback — 4× slower here, but 272 of them means the shortest
  queue, and for a chained run you aren't waiting on, availability can beat speed.

> **Worth deciding before spending the compute:** this project's own diagnosis is that the
> remaining errors are *training-coverage gaps, not capacity limits* — `docs/HANDOFF.md` holds the
> 500k/family scale-up until the coverage fixes are confirmed, and the cycle-five worklist sets an
> explicit diminishing-returns gate. Free compute removes the cost argument against scaling, but
> it doesn't answer whether scaling is the right next experiment. A cheap way to find out first:
> a **250k A/B at 0.8B** (~$15 rented, ~10 h on an A100) tells you whether more data helps at all
> before committing 170 GPU-hours to the family.

## The three things that are different from our previous runs

### 1. Inode quota → Apptainer overlay

Torch's filesystems: `/home` is **50 GB but only 30K inodes**, `/scratch` is **5 TB / 5M inodes,
purged after 60 days unused**, `/archive` is 2 TB / 20K inodes. A single `pip install torch`
exceeds the `/home` inode quota by itself, which is why NYU explicitly recommends against conda
environments in `/home`.

The cluster-recommended fix, which `00_setup_env.sh` implements, is to install miniconda and every
dependency **inside a mounted ext3 overlay image** (`/share/apps/overlay-fs-ext3/`, run against
`/share/apps/images/`) — so the ~150k dependency files occupy exactly one file on the shared
filesystem.

Setup mounts the overlay `:rw`; every job afterwards mounts it `:ro` (see `run_in_env` in
`env.sh`), which is what lets several jobs share one overlay. If a `:rw` mount is refused, NYU's
own examples pass `--fakeroot` — add it to the setup call. If you'd rather use a plain venv — or
uv, which NYU also documents and which suits this repo's PEP-723 scripts well — set
`USE_CONTAINER=0`, or see the note at the top of `00_setup_env.sh`.

Because `/scratch` is purged after 60 days of no access, **pushing adapters to the Hub is your
backup**, not a nicety.

Also note every cache (`HF_HOME`, `TORCH_HOME`, `TRITON_CACHE_DIR`) is redirected to `/scratch`
in `env.sh`. The HuggingFace default of `~/.cache/huggingface` is the same inode trap.

### 2. Assume no internet on compute nodes → pre-stage, then run offline

NYU doesn't document Torch's compute-node network policy either way, so this bundle assumes the
restrictive case — which is correct-either-way and costs nothing if the nodes turn out to be open.

`01_prefetch.sh` runs on the login node and `snapshot_download`s the base model into `$HF_HOME`.
Every job then sets `HF_HUB_OFFLINE=1`, which turns a cache miss into an immediate loud error
rather than a job that hangs for its whole wall-clock allocation on a dead network call.

The corollary: **don't use `--push-to-hub` during training.** Train offline, then push from the
login node with `40_push_adapter.sh`. (That also sidesteps a hazard this project already hit on
HF Jobs — per-epoch auto-push left a *partially trained* checkpoint sitting under the finished
run's name after a job was killed mid-run.)

### 3. Wall-clock limits → step checkpointing and requeue

`sft_qwen.py` previously only checkpointed once per epoch — every 1–4 hours depending on GPU. On
a cluster with a hard `--time` limit, hitting the limit at 90% through an epoch loses everything
since the last one. Two flags were added for this (default-off, so nothing else about the
project's training path changes):

- `--save-steps 500` — checkpoint every 500 steps, with `--save-total-limit 2` for disk hygiene
- `--resume-from-checkpoint auto` — resume the newest checkpoint in `--output-dir` if there is
  one, start fresh if there isn't

Because `auto` is a no-op on a fresh directory, `20_train.sbatch` passes it unconditionally and
carries `#SBATCH --requeue`. A wall-clock kill or preemption costs minutes: resubmit the exact
same command and it picks up where it left off.

## Verifying the run is actually correct

This project lost real time to two silent failures. Both are now checked automatically, but know
what you're looking for in the logs:

**The vision-tower / load-class bug.** Qwen3.5 is multimodal — it carries a vision tower — and
LoRA's `target_modules="all-linear"` will happily adapt it. Worse, if training loads the
multimodal class and eval loads the text-only one, the adapter keys don't match, PEFT warns
"missing adapter keys", **silently applies nothing**, and your fine-tuned model scores exactly
like an untrained one. The symptom is a trained model that performs at the base-model floor.

- `10_smoke.sbatch` runs `--dry-run` first; it must print **0 visual adapters**.
- `30_eval.sbatch`'s logs must show `loaded ... as AutoModelForImageTextToText` and must **not**
  show any "missing adapter keys" warning.

**Harmless noise you can ignore:** `fast path not available` (the kernel fallback — expected,
it's why this workload is ~3× slower than it looks like it should be) and
`[ERROR] loss/logits ... not documented` (a transformers docstring lint).

**A sanity floor:** `synth_dev` should score ~0.99 macro-F1. It's in-distribution, so anything
much below that means something is broken in the pipeline, not in the data. The interesting
numbers are the real gold sets — the current board (v4: 0.816 macro / 0.861 micro / 57.8% EM on
the 18-volume panel) is in `docs/HANDOFF.md`.

## Troubleshooting

| symptom | cause / fix |
|---|---|
| `Disk quota exceeded` during setup | inode quota — you're installing to `/home` (30K inodes) or ran `USE_CONTAINER=0`. Check `myquota`. Use container mode. |
| `sbatch: error: ... account` / job never queues | Torch **requires** `--account`. Run `my_slurm_accounts` and set `SLURM_ACCOUNT` in `env.sh`. |
| `Invalid feature specification` | `--constraint=$GPU_TYPE` names a feature your cluster doesn't use. Check the real feature names (`sinfo -o "%N %f"`) and fix `GPU_TYPE`. |
| **Job auto-cancelled mid-run for low GPU utilization** | Torch policy cancels jobs below a 10–60% utilization threshold. This workload is GPU-bound so it should sit well above that, but if you see it: you likely requested more GPUs than the 1 this uses, or the job stalled on I/O. Check `nvidia-smi` output in the log. |
| `apptainer: command not found` | older cluster with `singularity` instead — `env.sh` auto-detects, but set `APPTAINER_BIN` explicitly if it guessed wrong. |
| Job hangs, no output, dies at wall clock | a network call on a compute node. Confirm `HF_HUB_OFFLINE=1` is exported and `01_prefetch.sh` actually cached the model. |
| `CUDA out of memory` in `entropy_from_logits` | known: YAML targets are longer than pipe and full-vocab logits spike. Halve `BATCH_SIZE`, double `GRAD_ACCUM`. The `PYTORCH_CUDA_ALLOC_CONF` / `HF_DEACTIVATE_ASYNC_LOAD` escape hatches are already set in `20_train.sbatch`. |
| `torch.cuda.is_available()` False during setup | expected — you're on a login node, which has no GPU. Only a concern if it happens inside an sbatch job. |
| Trained model scores like an untrained one | the load-class bug above. Check for "missing adapter keys". |
| `SFTConfig got an unexpected keyword` | TRL version drift. `sft_qwen.py` filters unknown kwargs and logs `note: this TRL's SFTConfig has no 'x'; skipping it` — that note is fine. A hard error means something bigger changed; pin TRL. |
| Everything vanished from `/scratch` | purged after 60 days without access. Push adapters to the Hub; that's the backup. |

Useful: `my_slurm_accounts` (your allocations), `myquota` (disk + inodes), `squeue -u $USER`
(queue), `sacct -j <id> --format=JobID,State,Elapsed,MaxRSS` (what happened), `seff <id>`
(efficiency after the fact), `sinfo -o "%N %f %G"` (node features and GPUs).

## Regenerating the training data on the cluster

`synth_persons.py` is fully self-contained and needs no network, so you can regenerate rather
than ship data (`make_bundle.sh --no-data`):

```bash
run_in_env "python data_prep/synth_persons.py --profile mix --n 100000 --seed 13 \
              --target yaml --out $DATA/synth_train.jsonl --stats"
```

Use a different `--seed` for the smoke (7) and dev (99) sets so they don't overlap the train set.

## Porting to another cluster

The cluster-specific parts are all in `env.sh` and `00_setup_env.sh`:

- **Paths** — `PROJECT`, `CONTAINER_SIF`, `OVERLAY_SRC` point at Torch's `/share/apps`. Most
  clusters have an equivalent public container directory; ask the admins, or set
  `USE_CONTAINER=0`.
- **GPU selection** — `slurm_gpu_args` emits Torch's `--gres=gpu:1 --constraint=<type>`. Other
  sites use a typed `--gres=gpu:a100:1` (the Greene form), `--gpus-per-node`, or a GPU-specific
  partition. Edit that one function.
- **Account flag** — mandatory on Torch, often optional elsewhere. `slurm_gpu_args` omits it when
  `SLURM_ACCOUNT` is empty.
- **Partitions** — Torch says don't set them. Other clusters require it; add `--partition` to
  `slurm_gpu_args` if so.
- **Apptainer vs Singularity** — `env.sh` auto-detects via `APPTAINER_BIN`.
- **Module names** — `00_setup_env.sh` tries a couple of common ones and shrugs if none load.
- **Internet policy** — if compute nodes *do* have outbound access you can drop `HF_HUB_OFFLINE`,
  though pre-staging is still better practice.
- **Precision** — `sft_qwen.py` auto-selects bf16/fp16, so pre-Ampere cards (Turing/Volta, which
  Torch no longer has) still work without a flag.

The `sft_qwen.py` / `qwen_predict.py` / `evaluate.py` chain itself is portable — plain
PyTorch + transformers + TRL, single GPU, no cluster assumptions.

## Where the project actually stands

Read `docs/HANDOFF.md` first — it's the live project state. The one-paragraph version: we're
fine-tuning Qwen3.5-0.8B to parse one historical city-directory line into 8 structured fields,
training on synthetic data and evaluating on hand-labeled gold from 18 real NYC directory
volumes (1786–1933). The current model (v4) leads a prompt-primed Gemini baseline on macro-F1,
micro-F1, and per-volume wins. **The immediate next step is the v5 retrain** — the data is
generated and committed, only the training run is outstanding. That is exactly the run these
scripts are built to do.
